## Context

`zStep` (`moa-core/mcp/server.mjs:93`) is the single step shape for config pipelines, ad-hoc steps and the tool boundary. `opRunStart` (`:1624`) selects `chosen` steps (ad-hoc | named | default), writes the manifest (`steps`, `current: 0`, `loops`, …) and returns `frame` + `describeStep(0)`. `opStepReport`'s REVISE branch (`:1859`) resolves the loop target from `step.loopBackTo`, or the nearest previous non-gate non-master step, and errors if none. Everything downstream indexes `manifest.steps`, so filtering *before* the manifest is written leaves the rest of the state machine untouched. See proposal.md - Why.

## Goals / Non-Goals

**Goals:** one pipeline for fresh and pre-planned work; skips explicit and audited; zero behavior change when `provided` is absent; core stays source-agnostic (no tool or vendor names); **no blocker on a well-formed run** — every error is an authoring mistake, surfaced at run start with the fix.

**Non-Goals:** a predicate DSL (`when: exists(path)`); auto-detecting inputs from the filesystem; skipping by task size (named pipelines already cover that); re-pointing an **explicit** loop target to a different phase. Implicit targets are excluded from that last one — they are resolved fresh at report time today and stay that way.

## Decisions

- **`provided` names phases, not a separate vocabulary of input tokens.** An earlier draft had `unless: <input>` on the step plus `provided: [<input>]` on the run. The token's value only ever pointed back at a phase name, so the second namespace bought nothing and cost: a union-of-declared-tokens check to catch typos, a naming question for every input, and the ambiguity of one token meaning different things on different steps. With phase names, an unknown or non-skippable entry in `provided` is caught exactly and reported precisely.
- **`skippable: true` is a boolean because that is the whole job it does** — marking the step as opt-in-able by the run. Identity is already carried by `phase`.
- **`skippable` is forbidden on gates; only structure removes a gate.** `provided` is written by the run (the master); `requires` / `loopBackTo` are written by the config author. Keeping the run out of the gate set means a master cannot delete verification by declaration, however it words its `provided`. This replaces the earlier "the frame lists every skip, so over-declaring is visible" mitigation, which was self-certification — the master both writes and reads the frame.
- **A gate's parent defaults to its `loopBackTo`; `requires` overrides and extends it.** A gate exists to guard the phase it sends work back to, so the edge is already in the config and duplicating it would be a second source of truth that can drift. But the two are genuinely different edges — `loopBackTo` is control flow, `requires` is structure — so `requires` exists for children with no `loopBackTo` (`execute` → `q&a`) and for a gate whose parent is not its loop target. Critically, the default applies to **gates only**: `execute` carries `loopBackTo: plan` in all three shipped pipelines and must never inherit `plan`'s fate.
- **Cascade instead of fail-fast.** An earlier draft errored when a surviving gate's loop-back target had been skipped. Under cascade that state is unreachable: a gate naming a skipped phase is itself skipped. The remaining errors are all authoring mistakes, so a well-formed run never sees a blocker — which is the point, since the master is the one reading them mid-flight.
- **Filter in `opRunStart` right after `chosen` is selected**, iterating to a fixed point for the transitive cascade; manifest gets `provided` and `skipped: [{phase, reason}]`. `manifest.steps` = survivors, so `current`, `loops`, `producerFor`, `describeStep` and REVISE work unchanged.
- **The effort-ladder fallback is a bug fix this change exposes, not new behavior.** `describeStep` (`:1587`) reads `loops[s.loopBackTo ?? s.phase]` while REVISE (`:1866`) writes `loops[steps[ti].phase]`. The two agree only while the target survives. Skipping `plan` makes them permanently disagree for `execute` in every shipped pipeline, so the rung freezes at 0 across REVISE loops. Reading the step's own phase when the target is absent restores escalation without touching the surviving-target path.
- **The mutation floor is unchanged and is enforced behaviorally, not structurally.** `finish()` (`:1795`) walks actual writes and clears them against passed critical gates. A critical gate can only cascade away when its producer was skipped — in which case that producer wrote nothing. Any other write still needs a passed critical gate or the run finishes `done_unverified`. `DESIGN.md:46` currently says gates "can never be skipped"; that sentence is about master discretion and must be narrowed to say so.
- **Strict mode rejects `provided`.** `config.schema.json:77` defines strict as "every declared phase runs with its declared role×model, nothing skipped/merged/inlined". Honoring `provided` there would require rewording the guarantee CI and release runs depend on; rejecting it keeps that guarantee literal and costs one check.
- **Ad-hoc `steps` accept both fields** (same `zStep`), so an adaptive master can compose once and reuse with different `provided`.
- **Skill wording is source-agnostic**: "if the brief already carries what a phase would produce, name that phase in `provided`". OpenSpec briefs simply satisfy it.

## Risks / Trade-offs

- An input whose name differs from the phase producing it can no longer be expressed. Nothing in the shipped pipelines or the motivating case needs it, and `requires` covers the structural half; if it is ever needed, a step-level alias is additive.
- Cascade removes a gate without the author writing anything at that step. Mitigated by the frame naming each skipped phase and its reason, and by the cascade being derivable from the config alone — a reader can compute it from `loopBackTo` without knowing the run.
- A master could over-declare `provided` to dodge planning. It cannot dodge verification: `skippable` is illegal on gates, and the shipped templates mark only `plan`. The worst case is a run that trusts a plan it should not have — visible in the frame, and no different from the master writing a bad plan itself.
- Templates gain `skippable: true` on one step; custom pipelines opt in by adding the field — no silent behavior change for existing configs.
